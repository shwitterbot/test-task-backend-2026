# Ночная синхронизация amoCRM с PostgreSQL

Точка входа — `collect_leads_customers(is_full=True)` из `main.py`. Сначала обрабатываются покупатели, затем сделки.

## Что изменилось

- Вместо запросов и коммитов на каждую сущность CRM читается пакетами по 500 записей. Один SQL-запрос находит группы для всего пакета. Поиск по ID и логину внутри пакета идёт по словарям, которые обновляются при изменении логинов и слияниях. Новые и изменённые группы записываются отдельными многострочными командами.
- Покупатель без логина пропускается. При совпадении по логину учитывается число разных групп. Если сделка найдена по ID в одной группе, а по логину покупателя в другой, данные переносятся в группу сделки, исходная группа удаляется и сама сделка обновляется. Контакты и компании из выгрузки сохраняются, включая ссылки, у которых пришёл только ID.
- Полный прогон хранит наборы полученных ID по группам. После завершения обеих выгрузок PostgreSQL удаляет устаревшие вложенные записи, записи с «удалить» в имени и группы без актуальных покупателей и сделок. JSONB всей таблицы в Python для этого не читается. Ошибка CRM или БД откатывает всю транзакцию. Чтение таблицы другими сессиями доступно в ходе синхронизации, запись ждёт её окончания.
- Сохранены исходная таблица, формат `general` / `api_value`, связь сделки и покупателя через общий `abstract_customer.id` и `send_methods` у группы-получателя. Два GIN-индекса поддерживают точный поиск по ID, логину и названию через JSONB-оператор `@>`. Индексы обновляются сразу, чтобы повторные поиски во время прогона обходились без большой очереди отложенных записей.

## Стоимость прогона

При 20 000 покупателях и 50 000 сделках получается до 140 входных пакетов. Если каждый пакет требует один поиск и один тип записи, это 280 SQL-команд плюс до 140 команд очистки и две общие команды на блокировку и удаление. Смешанные вставки, обновления и слияния дают верхнюю оценку **662 SQL-команды** при настройках по умолчанию и **один COMMIT**. Служебные команды открытия соединения в оценку не входят. В исходном цикле только первичных поисков было до 70 000, ещё десятки тысяч операций приходились на изменения и коммиты.

На PostgreSQL 16 синтетический прогон на 20 000 покупателях и 50 000 сделках дал **382 SQL-команды** и **130 МиБ пикового RSS** Python-процесса при 50 000 итоговых группах и документах CRM около 1 КБ. Замер сделан с локальным PostgreSQL и генератором, который выдаёт сущности по одной. План поиска использовал оба GIN-индекса.

В Python находятся текущий пакет CRM, совпавшие группы и наборы ID для очистки. Для сопоставимых документов и связей ориентир составляет **130–160 МиБ** при 50 000–70 000 группах. Частый логин или большая группа могут увеличить память пакета, поскольку для разрешения неоднозначности нужно учесть все совпадения.

## Проверка

Python 3.9+, PostgreSQL 12+. Адаптер CRM в исходном задании отсутствует. В приложении `main.amocrm_get` должен быть подключён к адаптеру, который выдаёт `Customer` и `Lead` и пробрасывает ошибки выгрузки. Тесты подставляют такой итератор и используют настоящую БД в изолированных временных схемах.

```bash
python -m pip install -r requirements.txt 'pytest>=8,<9'
TEST_DATABASE_URL='postgresql+psycopg://user:password@localhost/crm_test' python -m pytest -q
```

Для новой базы `db.create_all()` создаёт таблицу и индексы. Для существующей таблицы примените миграцию. Во время построения индексов чтение таблицы доступно.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_crm_lookup_indexes.sql
```

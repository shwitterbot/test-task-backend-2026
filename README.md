# Ночная синхронизация amoCRM с PostgreSQL

Точка входа — `collect_leads_customers(is_full=True)` из `main.py` внутри Flask app context. Сначала обрабатываются покупатели, затем сделки. Python ≥ 3.9, PostgreSQL ≥ 12; локально проверяется Python 3.13 из `.python-version`.

## Что изменилось

- Вместо запросов и коммитов на каждую сущность CRM читается пакетами по 500 записей. Один SQL-запрос находит группы для всего пакета. Поиск по ID и логину внутри пакета идёт по словарям, которые обновляются при изменении логинов и слияниях. Новые и изменённые группы записываются отдельными многострочными командами.
- Покупатель без логина пропускается. При совпадении по логину учитывается число разных групп. Если сделка найдена по ID в одной группе, а по логину покупателя в другой, данные переносятся в группу сделки, исходная группа удаляется и сама сделка обновляется. Контакты и компании из выгрузки сохраняются, включая ссылки, у которых пришёл только ID.
- Полный прогон хранит наборы полученных ID по группам. После завершения обеих выгрузок PostgreSQL удаляет устаревшие вложенные записи, записи с «удалить» в имени и группы без актуальных покупателей и сделок. JSONB всей таблицы в Python для этого не читается. Ошибка CRM или БД откатывает всю транзакцию. Чтение таблицы другими сессиями доступно в ходе синхронизации, запись ждёт её окончания.
- Сохранены исходная таблица, формат `general` / `api_value`, связь сделки и покупателя через общий `abstract_customer.id` и `send_methods` у группы-получателя. Два GIN-индекса поддерживают точный поиск по ID, логину и названию через JSONB-оператор `@>`. Индексы обновляются сразу, чтобы повторные поиски во время прогона обходились без большой очереди отложенных записей.

## Стоимость прогона

При 20 000 покупателях и 50 000 сделках получается до 140 входных пакетов. Если каждый пакет требует один поиск и один тип записи, это 280 SQL-команд плюс до 140 команд очистки и две общие команды на блокировку и удаление. Смешанные вставки, обновления и слияния дают верхнюю оценку **662 SQL-команды** при настройках по умолчанию и **один COMMIT**. Служебные команды открытия соединения в оценку не входят. В исходном цикле только первичных поисков было до 70 000, ещё десятки тысяч операций приходились на изменения и коммиты.

Расчёт верхней границы: 140 поисков + до 140 вставок + до 140 обновлений + до 100 удалений групп в пакетах сделок + до 140 пакетов очистки + блокировка и окончательное удаление = **662**. Если в каждом пакете нужен только один тип записи, при 50–70 тыс. итоговых групп получается примерно **382–422 команды**. Внутри одного `SELECT` выполняется несколько индексных проверок: число команд не описывает всю работу PostgreSQL.

В Python находятся текущий пакет CRM, совпавшие группы и наборы ID для очистки. Сложность по памяти — `O(пакет + совпавшие JSON + полученные ID)`. При документах около 1 КБ и небольшом числе контактов/компаний ориентир составляет **130–160 МиБ RSS** при 50 000–70 000 группах, включая интерпретатор и библиотеки. Это оценка, не лимит: частый логин, большая группа или множество связанных ID увеличивают память. Адаптер должен выдавать итератор, не удерживающий всю выгрузку в списке. Полный объём в этой проверке не запускался.

## Что оставлено и почему

Сохранены JSONB и общий `abstract_customer.id`, чтобы не менять потребителей данных и связь сделки с покупателем. Нормализация таблиц для этой нагрузки не обязательна. GIN-индексы поддерживают точное совпадение названия через `@>`; поиск по части названия потребует отдельного индекса, если появится такое требование.

Одна транзакция обеспечивает откат всех изменений при ошибке, но удерживает блокировку записи и во время ожидания CRM. Чтение другими сессиями доступно. Ошибки адаптера должны пробрасываться наружу; успешная пустая полная выгрузка очищает таблицу. В `is_full=False` очистка не выполняется, сохранены прежние исключения статусов покупателей `111349` и сделок `143`. Celery, брокер и новые сервисы не добавлены.

## Проверка

Для разработки используется Python 3.13 (см. `.python-version`), PostgreSQL 12+. Не используйте предварительные сборки Python 3.15: зависимости с бинарными модулями могут быть несовместимы с ними. Адаптер CRM в исходном задании отсутствует. В приложении `main.amocrm_get` должен быть подключён к адаптеру, который выдаёт `Customer` и `Lead` и пробрасывает ошибки выгрузки. Тесты подставляют такой итератор и используют настоящую БД в изолированных временных схемах.

Подготовка Python-окружения (один раз):

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Для уже подготовленной локальной тестовой БД запустите из корня проекта:

```bash
TEST_DATABASE_URL='postgresql+psycopg://crm_test@127.0.0.1:55432/crm_test' .venv/bin/python -m pytest -q
```

Без `TEST_DATABASE_URL` тесты пропускаются. Пользователю тестовой БД нужно право создавать схемы. Для другой БД укажите её реальные реквизиты и порт в `TEST_DATABASE_URL`.

Для отдельной локальной тестовой БД на macOS с Homebrew PostgreSQL 15:

```bash
# Если PostgreSQL ещё не установлен:
brew install postgresql@15
export PATH="$(brew --prefix postgresql@15)/bin:$PATH"
# Выполняется один раз после создания .venv:
initdb -D .venv/postgres-test -U crm_test --auth-local=trust --auth-host=trust --encoding=UTF8 --locale=C
pg_ctl -D .venv/postgres-test -l .venv/postgres-test/server.log -o '-h 127.0.0.1 -p 55432' -w start
createdb -h 127.0.0.1 -p 55432 -U crm_test crm_test
TEST_DATABASE_URL='postgresql+psycopg://crm_test@127.0.0.1:55432/crm_test' .venv/bin/python -m pytest -q
```

Эта БД слушает только локальные TCP-подключения и используется без пароля исключительно для тестов. После перезагрузки повторите команду `pg_ctl ... start`; `initdb` и `createdb` повторять не нужно. Для остановки: `pg_ctl -D .venv/postgres-test -m fast -w stop`.

В PyCharm выберите интерпретатор `.venv/bin/python` и конфигурацию **Sync tests (local PostgreSQL)**: в ней уже задан адрес этой тестовой БД. Если конфигурация ещё не появилась, переоткройте проект, чтобы IDE загрузила файл из `.run/`.

Для новой базы `db.create_all()` создаёт таблицу и индексы. Для существующей таблицы примените миграцию. Во время построения индексов чтение таблицы доступно.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_crm_lookup_indexes.sql
```
